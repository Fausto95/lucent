Your app imports a module like any TypeScript file, but none of its code runs as JavaScript. Five steps turn it into C++ in the app binary, and the import into calls to that C++.

<Steps>

1. ### TypeScript checks the module

   <Diagram name="build-check" />

   Lucent runs the TypeScript compiler on every module, in strict mode with `noUncheckedIndexedAccess`, so each type comes from TypeScript's own checker.

   Then Lucent applies [the language's rules](/docs/api/language/). Code that breaks one stops the build with a `LUCENT` [diagnostic](/docs/api/diagnostics/), and the native package stays as it was. Lucent's editor plugin shows these diagnostics as you type.

2. ### Lucent writes C++, and Swift or Kotlin where an API needs it

   <Diagram name="build-cpp" />

   Each module becomes a C++ file and a header, one pair per platform when your app has platform code. On iOS, a module that uses iOS APIs is Objective-C++. The files' `#line` directives point back to your source, so compiler errors, the debugger and crash reports name `.lucent.ts` lines.

   The C++ keeps JavaScript's behavior: a `number` is a `double` with JavaScript's arithmetic, strings are UTF-16, and objects are shared by reference. The few [differences](/docs/api/language/differences/) are listed.

   An SDK call becomes an Objective-C message send or a JNI call. An API only Swift or Kotlin can call gets a generated Swift or Kotlin function. There's no Swift or Kotlin to write ([SDK bindings](/docs/architecture/sdk-bindings/)).

3. ### `lucent build` writes the native package

   <Diagram name="build-package" />

   The native package, `.lucent/native`, holds the C++ runtime, your modules' C++, the generated Swift and Kotlin, the build files and a proxy per module. The modules of the [Lucent packages](/docs/architecture/packages/) your app depends on compile into the same package, with one runtime.

   `.lucent/` is generated, so keep it out of git; [the .lucent directory](/docs/api/lucent-directory/) lists its files. A build rewrites only the files whose content changed.

4. ### Your app's build compiles it

   <Diagram name="build-app" />

   React Native's autolinking finds the native package through the `lucent` entry of `react-native.config.js`. On iOS, CocoaPods compiles it, and it registers itself as the app loads. On Android, Gradle adds its CMake project to the app's native build.

   Either way, one C++ TurboModule named `Lucent` serves every module, with no codegen step. Metro's watcher, the Expo config plugin and a Gradle task run `lucent build` for you ([integrations](/docs/api/integrations/)). Editing a module changes native code, so the app needs a native rebuild: a JavaScript reload keeps the old code ([Apply a change](/docs/guides/apply-a-change/)).

5. ### Metro bundles a proxy in the module's place

   <Diagram name="build-metro" />

   ```js title=".lucent/native/js/greet.js" include="proxy/greet.js"
   ```

   Your editor and `tsc` read the `.lucent.ts` source, so the import is typed. Metro bundles this proxy instead, so none of the module's code is in the JS bundle.

   A module that was never built gets a proxy that throws `Lucent: greet.lucent.ts has not been compiled`.

</Steps>

## What happens when the app loads a module

The proxy's `loadModule` reads the module from the `Lucent` TurboModule, which builds its exports once per JavaScript runtime. First it checks that the app's native code is what this JavaScript was built against.

Each build stamps its output with the runtime's ABI version, a hash of the program and a hash of each module's exports. Native code whose exports differ from what the JavaScript expects can't be called safely. Loading it throws an error whose `code` is `LUCENT_NATIVE_MISMATCH`, naming the fix.

The same exports from another build of the program load with a warning, since the installed implementation runs. [Stale native code](/docs/architecture/builds/) has every case.

After that, each exported function is a JSI host function. A call reaches your C++ directly, with no message queue or JSON in between ([the boundary](/docs/architecture/boundary/)).

## What runs where

- Synchronous exports run on the JS thread, while JavaScript waits.
- `async` exports run on their package's thread, a background thread.
- `main(() => …)` runs on the main thread, and `compute` tasks on a pool of worker threads.

[Threads](/docs/architecture/threads/) explains how they share work, and [memory](/docs/architecture/memory/) when native objects go away.
