`lucent build`, `lucent check`, `lucent dev` and the [editor plugin](/docs/api/integrations/#editor-plugin) report the same diagnostics. A build with one writes nothing. `lucent explain <code>` prints the explanation this page shows.

Codes are stable, and grouped by what they are about. A warning still compiles; every other diagnostic stops the build.

## Syntax and built-ins (1xxx)

### LUCENT1001

**Syntax outside the subset**

Lucent compiles a subset of TypeScript whose every construct has a native equivalent with the same behaviour. `var` (function scoping and hoisting), accessors in object literals, `await using`, a generic function used as a value and `this` outside a class member fall outside it.

**Fix:** rewrite it with the supported form: `let`/`const` for `var`, a class for an object with accessors.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
export function total(xs: number[]): number {
  var sum = 0;
  for (const x of xs) sum += x;
  return sum;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
export function total(xs: number[]): number {
  let sum = 0;
  for (const x of xs) sum += x;
  return sum;
}
```

</TabItem>
</Tabs>

### LUCENT1002

**Unsupported operator**

Objects in Lucent have a fixed native layout, so `delete`, which removes a property at run time, has no native equivalent. An object type stores its optional fields even when unset, so `in` can't answer as JavaScript does on one. Two functions can't be compared: a function value has no stable identity (a named function is a new value at each use).

**Fix:** use a Map or Record for changing keys, compare an optional field with `undefined`, and tell union members apart by a discriminant.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
export function clear(tags: { name?: string }): { name?: string } {
  delete tags.name;
  return tags;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
export function clear(tags: { name?: string }): { name?: string } {
  tags.name = undefined;
  return tags;
}
```

</TabItem>
</Tabs>

### LUCENT1003

**Built-in without a native implementation**

Every built-in a module calls runs as native code from the Lucent runtime. The ones the language reference lists behave as in JavaScript, apart from the differences it gives reasons for. The rest are reported rather than approximated, as are arguments Lucent cannot honor exactly (a locale, a cause that isn't an `Error`).

**Fix:** use a built-in Lucent implements, or write the helper in the module.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
export function listed(xs: number[]): string {
  return xs.toLocaleString();
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
export function listed(xs: number[]): string {
  return xs.join(",");
}
```

</TabItem>
</Tabs>

### LUCENT1004

**Unsupported destructuring**

Computed keys (`{ [key]: value }`) would need a dynamic lookup, which no fixed native layout has. An object rest (`{ a, ...rest }`) copies the fields its type names into a new object. A record's rest is a new record, and a class instance has none.

**Fix:** name the fields you need, or read the one the key names with a condition.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
type Size = { width: number; height: number };
export function side(s: Size, key: "width" | "height"): number {
  const { [key]: value } = s;
  return value;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
type Size = { width: number; height: number };
export function side(s: Size, key: "width" | "height"): number {
  return key === "width" ? s.width : s.height;
}
```

</TabItem>
</Tabs>

### LUCENT1005

**Unsupported class feature**

Classes compile to C++ classes, so a subclass of `Map` or `Array` would inherit the runtime's container internals. An override whose parameters or result differ from the base method's can't share its native slot. A decorator runs when the class is defined and may replace the class or member it decorates, which a compiled class can't be.

**Fix:** hold the built-in in a field instead of extending it, and keep overrides' signatures the same as the base method's. Initialize statics in their declarations, and call decorators yourself.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
class Counts extends Map<string, number> {}
export function size(): number {
  return new Counts().size;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
class Counts {
  readonly map = new Map<string, number>();
}
export function size(): number {
  return new Counts().map.size;
}
```

</TabItem>
</Tabs>

### LUCENT1006

**Throwing a value that is not an Error**

Errors cross into JavaScript as `Error` objects with a name, a message and a stack that points at the Lucent source. A thrown string or number has none of that and no native type to catch it by.

**Fix:** throw `new Error(…)`, a built-in error such as `TypeError`, or a class that extends `Error`.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
export function port(text: string): number {
  const n = Number(text);
  if (!Number.isInteger(n)) throw "not a port";
  return n;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
export function port(text: string): number {
  const n = Number(text);
  if (!Number.isInteger(n)) throw new RangeError(`not a port: ${text}`);
  return n;
}
```

</TabItem>
</Tabs>

### LUCENT1007

**Call Lucent cannot compile**

A callback API's report is a value, which JavaScript would adopt if it were a promise: native code can't. A borrow lends bytes to the callback it is given, which must be written there to be checked. A platform class without an initializer has no native constructor to call.

**Fix:** await the promise and report its value, write the callback in the call, or make the object the way the SDK does.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
import { fromCallback } from "lucent:core";
export function later(p: Promise<number>): Promise<Promise<number>> {
  return fromCallback<Promise<number>>((resolve) => resolve(p));
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
import { fromCallback } from "lucent:core";
export function later(p: Promise<number>): Promise<number> {
  return fromCallback<number>((resolve) => {
    void p.then(resolve);
  });
}
```

</TabItem>
</Tabs>

### LUCENT1008

**Assignment to something that cannot be assigned**

Assignments write to a native variable or field. A function, an import, or a field the value's type does not have is not one.

**Fix:** assign a variable or a field the type declares.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
function tick(): number {
  return 1;
}
export function reset(): void {
  // @ts-expect-error: assigning a function
  tick = () => 0;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
let tick = (): number => 1;
export function reset(): void {
  tick = () => 0;
}
export function now(): number {
  return tick();
}
```

</TabItem>
</Tabs>

### LUCENT1009

**Loop over a value that is not iterable**

`for…of` works on arrays, strings, maps, sets, typed arrays and generators, and `for await` on those and channels. `for…in` works on records and arrays. An object type records neither which optional fields are set nor their order.

**Fix:** loop over an array (`Object.keys`, `Array.from`), or make the value a record.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
type Totals = { a: number; b: number };
export function sum(t: Totals): number {
  let s = 0;
  for (const k in t) s += k.length;
  return s;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
export function sum(t: Record<string, number>): number {
  let s = 0;
  for (const k in t) s += k.length;
  return s;
}
```

</TabItem>
</Tabs>

### LUCENT1010

**Await on a native object**

A native object reports its completion through its own API, usually a listener, so awaiting it would give the object back at once. Lucent does not recognize libraries by class name, so it cannot pick that API for you. `fromCallback` from `lucent:core` turns the listener into a promise: register it, then call `resolve` or `reject` from it.

**Fix:** wrap the listener or callback that reports its completion in fromCallback (lucent:core), and await that.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
import { PLATFORM } from "lucent:platform";
import { CompletableFuture } from "lucent:android/java.util.concurrent";
export async function ready(): Promise<boolean> {
  if (PLATFORM !== "android") return true;
  const value = await CompletableFuture.completedFuture("ready");
  return value !== null;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
import { fromCallback } from "lucent:core";
import { PLATFORM } from "lucent:platform";
import type { Throwable } from "lucent:android/java.lang";
import { CompletableFuture } from "lucent:android/java.util.concurrent";
export async function ready(): Promise<boolean> {
  if (PLATFORM !== "android") return true;
  const future = CompletableFuture.completedFuture("ready");
  const value = await fromCallback<string | null>((resolve, reject) => {
    future?.whenComplete((v: string | null, failure: Throwable | null) => {
      if (failure) reject(new Error(failure.getMessage() ?? "failed"));
      else resolve(v);
    });
  });
  return value !== null;
}
```

</TabItem>
</Tabs>

## Types and the boundary (2xxx)

### LUCENT2001

**Value without a native type**

Native code needs to know each value's layout at compile time. `any` gives it none, and `unknown` only stands for a caught error, whose type JavaScript does not say.

**Fix:** use a concrete type, a union, or a generic parameter.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
export function size(value: any): number {
  return value.length;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
export function size(value: string): number {
  return value.length;
}
```

</TabItem>
</Tabs>

### LUCENT2002

**Type without a native representation**

Each type maps to one native representation. An intersection can combine unrelated layouts, `symbol` is not implemented yet, and `object` says nothing about the layout. A native member whose types cannot cross yet is named with its symbol and artifact: wrap it in Swift or Kotlin of your own.

**Fix:** spell the combined type out as one object type, or use a concrete type. Take an array instead of a function type's rest parameter. Call a function taking a rest parameter; don't pass it.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
type Named = { name: string };
type Aged = { age: number };
export function label(p: Named & Aged): string {
  return `${p.name} (${p.age})`;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
type Person = { name: string; age: number };
export function label(p: Person): string {
  return `${p.name} (${p.age})`;
}
```

</TabItem>
</Tabs>

### LUCENT2003

**Object used as a type with a different shape**

Object types with the same fields share one native struct. TypeScript lets a value with more fields stand for a type with fewer. Natively they are different structs, and the extra fields would have nowhere to go.

**Fix:** pass exactly the fields the type declares, or widen the parameter's type.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
type Point = { x: number; y: number };
type Point3 = { x: number; y: number; z: number };
function norm(p: Point): number {
  return Math.hypot(p.x, p.y);
}
export function flat(p: Point3): number {
  return norm(p);
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
type Point = { x: number; y: number };
type Point3 = { x: number; y: number; z: number };
function norm(p: Point): number {
  return Math.hypot(p.x, p.y);
}
export function flat(p: Point3): number {
  return norm({ x: p.x, y: p.y });
}
```

</TabItem>
</Tabs>

### LUCENT2004

**Collection used with another element type**

Arrays of `number` and of `number | string` have different native element types, and writes through the wider type wouldn't fit. Each instantiation of a generic class (`Box<number>`, `Box<number | undefined>`) is also a native class of its own. A `new` is built as the instantiation its value becomes, but an existing instance can't be converted: a copy would be another object.

**Fix:** annotate the collection with the element type it is used as.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
function first(xs: (number | string)[]): string {
  return String(xs[0]);
}
export function f(): string {
  const xs = [1, 2];
  return first(xs);
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
function first(xs: (number | string)[]): string {
  return String(xs[0]);
}
export function f(): string {
  const xs: (number | string)[] = [1, 2];
  return first(xs);
}
```

</TabItem>
</Tabs>

### LUCENT2005

**Union JavaScript values cannot be told apart by**

A value from JavaScript carries no type, so Lucent decides which union member it is from the value itself. Object members need a string-literal field, such as `kind`, whose value names the member.

**Fix:** add a string-literal field such as `kind: "circle"` to each object member.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
export function area(shape: { radius: number } | { side: number }): number {
  return "radius" in shape ? Math.PI * shape.radius ** 2 : shape.side ** 2;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
export function area(shape: { kind: "circle"; radius: number } | { kind: "square"; side: number }): number {
  return shape.kind === "circle" ? Math.PI * shape.radius ** 2 : shape.side ** 2;
}
```

</TabItem>
</Tabs>

### LUCENT2006

**Value that cannot cross the JavaScript boundary**

Exports convert their parameters and results between JavaScript and native values. Some native values have no JavaScript form: a generator's state, a platform object, a signal made in native code.

**Fix:** return plain data (an array instead of a generator, fields instead of a platform object).

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
export function* count(n: number): Generator<number> {
  for (let i = 0; i < n; i++) yield i;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
function* count(n: number): Generator<number> {
  for (let i = 0; i < n; i++) yield i;
}
export function counted(n: number): number[] {
  return [...count(n)];
}
```

</TabItem>
</Tabs>

### LUCENT2007

**Generic export**

Generics compile to C++ templates, instantiated for the types the module uses. JavaScript calls an export without types, so there is no instantiation to call.

**Fix:** keep the generic function private and export concrete wrappers.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
export function last<T>(items: T[]): T | undefined {
  return items[items.length - 1];
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
function last<T>(items: T[]): T | undefined {
  return items[items.length - 1];
}
export function lastName(names: string[]): string | undefined {
  return last(names);
}
```

</TabItem>
</Tabs>

### LUCENT2008

**Interface not declared with implements**

An interface with methods compiles to an abstract C++ base class that only classes declaring `implements` derive from. A class matching it only by shape is not one, nor is an object literal for an interface with a method or type parameters. A literal of a non-generic interface of properties alone is one.

**Fix:** add `implements` to the class, or use a class that declares it in place of the object literal.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
interface Shape { area(): number }
class Square {
  constructor(readonly side: number) {}
  area(): number {
    return this.side ** 2;
  }
}
export function area(): number {
  const s: Shape = new Square(2);
  return s.area();
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
interface Shape { area(): number }
class Square implements Shape {
  constructor(readonly side: number) {}
  area(): number {
    return this.side ** 2;
  }
}
export function area(): number {
  const s: Shape = new Square(2);
  return s.area();
}
```

</TabItem>
</Tabs>

### LUCENT2009

**Method signature differs from the interface's**

### LUCENT3011

**Code that cannot run in a compute task**

A compute task runs on a worker thread while module code keeps running, so it may only touch its input and what it makes. Module state, non-literal constants (a reload assigns them again), main-thread native code, function values the compiler cannot follow, `await` and timers break that rule. The message gives the path, through every call, to what breaks it.

**Fix:** pass what the task needs as its input, and apply its result where you await it.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"
import { compute } from "lucent:core";
const weights: number[] = [1, 2, 3];
function score(x: number): number {
  return x * (weights[0] ?? 1);
}
export async function run(x: number): Promise<number> {
  return await compute(score, x);
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
import { compute } from "lucent:core";
const weights: number[] = [1, 2, 3];
function score(job: { x: number; weights: number[] }): number {
  return job.x * (job.weights[0] ?? 1);
}
export async function run(x: number): Promise<number> {
  return await compute(score, { x, weights });
}
```

</TabItem>
</Tabs>

### LUCENT3012

**Value that cannot cross to a compute task**

A compute task's input is copied at submission, and its result comes back to the caller. Both must be numbers, strings, booleans, arrays, tuples, records, maps, sets, byte arrays, dates, or objects made of those. Functions, promises, main-thread native objects and values of unknown or generic type cannot cross, and the message names which part.

**Fix:** pass the data the task needs, and keep functions, signals and native objects on the calling side.

```ts title="example.lucent.ts (wrong)"
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"

```

</TabItem>

### LUCENT3021

**Component prop, event or command that cannot cross**

Props, event arguments and command arguments and results are plain data: numbers, strings, booleans, string literal unions, arrays and plain objects, possibly null. A function prop is an event named `on…`, whose call from the view posts its arguments to JavaScript, so it returns nothing. `key`, `ref`, `children` and `style` belong to React and the host.

**Fix:** pass plain data, make events return nothing, and name them onSomething.

### LUCENT3032

**Code that cannot run on an executor**

Code on an executor runs on its thread while module code keeps running, so the two share nothing either can change. In a function or object given to on(), module state, computed constants, main-thread native code, unknown code and `await` break that rule. It holds only constants, channels, emitters and executors, and an object is made only in on() and keeps `this` to itself.

**Fix:** send what it makes through a Channel made beside it, and keep module state on the module's thread.

<Tabs>
<TabItem label="✗ example.lucent.ts">

```ts title="example.lucent.ts (wrong)"

import { executor, on } from "lucent:thread";
let runs = 0;
export function start(): number {
  if (PLATFORM !== "android") return runs;
  const worker = executor("worker");
  CompletableFuture.runAsync(
    on(worker, () => {
      runs++;
    }),
    worker,
  );
  return runs;
}
```

</TabItem>
<TabItem label="✓ example.lucent.ts">

```ts title="example.lucent.ts (right)"
import { Channel } from "lucent:core";
import { PLATFORM } from "lucent:platform";
import { CompletableFuture } from "lucent:android/java.util.concurrent";
import { executor, on } from "lucent:thread";
let runs = 0;
export async function start(): Promise<number> {
  if (PLATFORM !== "android") return runs;
  const worker = executor("worker");
  const done = new Channel<number>("latest");
  CompletableFuture.runAsync(
    on(worker, () => {
      done.send(1);
    }),
    worker,
  );
  runs += (await done.receive()) ?? 0;
  return runs;
}
```
