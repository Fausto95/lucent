Module code is a module's exports, what runs after their `await`s, and the callbacks it registers. Modules that import one another, such as a package's, share a lock and a thread: an actor.

A package's code runs one turn at a time, like JavaScript, whichever thread it's on. Other packages, compute tasks and view code run while it does.

## Example

```ts title="crunch.lucent.ts"
import { delay } from "lucent:core";

let done = 0;

/** Synchronous: runs on the JS thread, between two turns of crunch(). */
export function progress(): number {
  return done;
}

/** Async: runs on this package's thread. */
export async function crunch(values: number[]): Promise<number> {
  let sum = 0;
  for (let i = 0; i < values.length; i++) {
    sum += values[i]!;
    done = i + 1;
    if (i % 10_000 === 9_999) await delay(0); // ends the turn: a waiting progress() runs now
  }
  return sum;
}
```

Without the `await delay(0)`, a call to `progress()` from JavaScript would wait until `crunch` returned.

## Where each kind of code runs

| --- | --- | --- |
| A synchronous export, method, getter, setter or constructor that JavaScript calls | The JS thread, while JavaScript waits | Yes |
| The argument checks of an `async` export or method | The JS thread, before the call returns | Yes |
| An `async` export or method that JavaScript calls, from its first line, and module code after an `await` | Its package's thread | Yes |
| A JavaScript callback that module code calls | The JS thread: at once during a synchronous call, else posted | Yes |
| The function passed to `main(f)` | The main thread, once its package is free | Yes |
| An SDK callback the platform waits for: it returns a value, fills an out-parameter, throws in Swift, or runs during the SDK call | The thread the platform calls it on (on the main thread, it waits only for the code holding its package then) | Yes |
| An iOS block or requirement Swift runs on the main thread, such as a UIKit delegate's method, even one returning `void`. | Any other SDK callback, such as a listener, an Android method returning `void`, or another delegate method | Posted to its package's thread | Yes |
| A handler of `onActivityEvent` from `lucent:android` | Posted to the context that subscribed: its package's thread, for module code | Yes |

| A component's setup, effects and commands, and the callbacks it gives the platform | The main thread, in the main context | No |

## Packages and their locks

- Modules that import one another share a lock and a thread: an actor. A package's modules, and an app's own, are one each, unless they import one another. Two pieces of one package's code never run at once, so module state has no data races.
- Packages run in parallel. A long job in one delays neither another nor the main thread.
- Module code runs in turns. A turn is a job and the `await` continuations it queues, and it holds its package's lock from start to end.
- An `await` on a promise that has already settled continues in the same turn. An `await` that has to wait, such as `await delay(0)`, ends the turn.
- The lock is fair: threads get it in the order they asked. A synchronous call from JavaScript waits for the current turn to end, then runs before the next one.
- It is reentrant. Module code that calls a JavaScript callback, which calls into Lucent again, goes on without waiting.
- The main thread never waits behind queued work. `main(f)` and lifecycle listeners start once the package is free. A delegate method that must answer waits only for the code holding the lock, ahead of anything queued.
- Debug builds log a main-thread wait over 50 ms. While module code calls a JavaScript callback, the main thread may run the package's code, as that JavaScript could.
- A JavaScript callback can call another package, which then waits for that package's lock. A wait that would close a cycle, with two threads each holding one package and waiting for the other, throws an `Error` (`Lucent: deadlock: …`) instead of hanging.

Keep turns short. Split a long loop with `await delay(0)`, and move heavy work to a compute task. [Run work off the JS thread](/docs/guides/run-work-off-the-js-thread/) shows both.

## main(f)

- `main(f)` from [lucent:thread](/docs/api/lucent-thread/#main) runs `f` on the main thread: the main queue on iOS, the main Looper on Android. It returns a promise of `f`'s result.
- `f` runs holding its package's lock, so it can use module state. The main thread doesn't wait for it: `f` starts once the package is free, so a running turn delays `f`, not the main thread. Keep `f` short.
- The caller doesn't wait for the main thread. In module code, what follows `await main(f)` runs on its package's thread.
- `f` can't be `async` ([LUCENT1007](/docs/api/diagnostics/#lucent1007)), and `main` is called in platform code, such as a platform branch ([LUCENT3004](/docs/api/diagnostics/#lucent3004)).

A main-thread-only SDK API compiles only on the main thread ([LUCENT3006](/docs/api/diagnostics/#lucent3006)). That is `f`, a function or method the SDK or `lucent:ios` calls on the main thread, a main-thread iOS subclass's members, and view code.

An Android `@WorkerThread` API called there compiles with a warning ([LUCENT3009](/docs/api/diagnostics/#lucent3009)).

[Run code on the main thread](/docs/guides/run-on-the-main-thread/) is the task.

## Compute tasks

- `compute(task, input)` from [lucent:core](/docs/api/lucent-core/#compute) runs `task` on a pool of worker threads, one fewer than the cores, and at least one.
- Tasks run in parallel with each other and with module code. They never take a package's lock.
- A task can't touch what module code shares: module state, main-thread or unknown native code, or anything asynchronous ([LUCENT3011](/docs/api/diagnostics/#lucent3011)).
- Its input is copied when `compute` is called, except a `NativeBuffer`, which moves ([lucent:core](/docs/api/lucent-core/#nativebuffer)). Its result comes back to the caller. Both must be data ([LUCENT3012](/docs/api/diagnostics/#lucent3012)).

## Executors

An executor is a serial thread of its own, outside any package's lock: a callback on it never waits behind module code. It's for callbacks that come often and can't wait, such as a camera's frames; here a one-shot location fix shows the shape.

```ts title="fix.lucent.ts"
import { Channel } from "lucent:core";
import { PLATFORM } from "lucent:platform";
import { LocationManager } from "lucent:android/android.location";
import { appContext, available } from "lucent:android";
import { executor, on } from "lucent:thread";

/** The device's latitude, read on an executor: never behind other module code. */
export async function latitude(): Promise<number> {
  if (PLATFORM === "ios") throw new Error("Android only, in this sample");
  if (!available("android", 30)) throw new Error("Needs Android 11");
  const manager = appContext().getSystemService(LocationManager);
  if (!manager) throw new Error("No location service");

  const fixes = executor("location.fixes");
  const latitudes = new Channel<number>("latest");
  manager.getCurrentLocation(
    LocationManager.GPS_PROVIDER,
    null,
    fixes,
    on(fixes, (fix) => {
      latitudes.send(fix ? fix.getLatitude() : 0);
    }),
  );
  return (await latitudes.receive()) ?? 0;
}
```

- `executor(label)` from [lucent:thread](/docs/api/lucent-thread/) makes one. An SDK parameter that takes a queue, on iOS, or a `java.util.concurrent.Executor`, on Android, takes it as it is.
- `on(executor, f)` hands `f` to the platform, as an SDK call's argument and only there ([LUCENT1007](/docs/api/diagnostics/#lucent1007)). `f` is a function literal: a block on iOS, a lambda or a functional interface on Android.
- When the platform calls `f` on the executor, it runs there at once. Called from another thread, an `f` that returns nothing runs in a turn of the executor. One that returns a value is reported as an error.
- `f` runs beside module code, so it can't use module state, main-thread native code or anything asynchronous ([LUCENT3032](/docs/api/diagnostics/#lucent3032)). Unlike a compute task, it may use native code of unknown thread, such as the frame it's given.
- It captures only `const` numbers, strings, booleans and bigints, channels and executors, made in the function that hands it over. What it makes leaves through a channel.
- To tell JavaScript, it emits on an `EventEmitter` it holds: capture the module's as a `const` (`const ev = events`), then call `ev.emit(…)` in `f`. The emit copies its arguments and runs in the package that made the `EventEmitter`, which calls the listeners.
- The callbacks it hands the platform go on an executor with `on()` too. One handed over without `on()` runs in its package, beside the executor, so it may capture only the same values.
- A delegate or a listener goes on an executor where it's made, as in `parser.delegate = on(frames, new Collector(out))`. Its class is then made only in `on()`, isn't exported and extends no class. It uses `this` only for its own members, so nothing but the platform reaches it. Its constructor takes only the values `f` may capture, and its methods follow `f`'s rules ([LUCENT3032](/docs/api/diagnostics/#lucent3032)).
- To hand a function or an object over more than once, keep it in a `const` in the function that makes it: `const listener = on(fixes, (fix) => …)`. Each use must pass it to an SDK call or property ([LUCENT1007](/docs/api/diagnostics/#lucent1007)). It's one platform object each time, so `removeUpdates(listener)` removes what was added.

## Channels

A `Channel<T>` from [lucent:core](/docs/api/lucent-core/#channel) carries values from a producer to a consumer. A compute task can send its results to module code as it runs. A channel in a task's input crosses as itself, so both ends share it.

```ts title="scan.lucent.ts"
import { Channel, compute } from "lucent:core";

function scan(input: { rows: number[][]; progress: Channel<number> }): number {
  for (let i = 0; i < input.rows.length; i++) input.progress.send(i + 1);
  input.progress.close();
  return input.rows.length;
}

export async function scanned(rows: number[][]): Promise<number[]> {
  const progress = new Channel<number>("lossless", 64);
  const seen: number[] = [];
  const done = compute(scan, { rows, progress });
  for (let n = await progress.receive(); n !== undefined; n = await progress.receive()) seen.push(n);
  await done;
  return seen;
}
```

- `send` never waits for the consumer. When the channel is full, its policy decides: `"lossless"` refuses the send, `"latest"` keeps only the newest value, `"drop"` drops the oldest.
- A send copies its value, as a task's input is copied, and moves a `NativeBuffer`. A value the channel drops, or that nobody receives, is released: a `NativeBuffer` is closed.
- `receive()` settles on the context that called it, with the next value, or `undefined` once the channel is closed and drained. Tasks can't receive ([LUCENT3011](/docs/api/diagnostics/#lucent3011)).
- `subscribe(onValue)` calls `onValue` with each value, one at a time, on the context that subscribed. It stops when the channel is closed and drained, or when you call `remove()` on what it returns.
- `stats()` counts what was sent, received, dropped and refused, and how many values wait.
- A channel doesn't cross to JavaScript ([LUCENT2006](/docs/api/diagnostics/#lucent2006)).

## The main context

View code runs on the main thread, in the main context. It's a component's setup, its effects and commands, and the callbacks it gives the platform.

The main context never takes a package's lock, so a view never waits behind module code. Without the lock, view code can't use module state ([LUCENT3022](/docs/api/diagnostics/#lucent3022)). Views are experimental: [Native views](/docs/architecture/views/) has the rest.

### Main-thread state

A module variable that only main-thread code uses is the main thread's. That code is components and `main(f)` callbacks, and the functions only they call. Views may read and write it, since each use runs on the one main thread.

- It holds plain values or native objects: a `Map<number, AVPlayer>` of players, say.
- A collection is used through its members (`players.get(id)`), never passed, returned or stored elsewhere.
- It starts as a literal or an empty collection, and assignments give it new ones.
- Its module's initialization assigns it on the main thread, so a reload never races a view still showing.

Module code reaches it through `main(f)`. A class JavaScript makes can keep its native object there, under an id a view takes as a prop.

## Where promises settle

- A promise settles on the context that made it. Code that awaits it resumes on its own context, and a result from another thread is posted there.
- So module code resumes on its package's thread after awaiting `main(f)`, `compute`, a JavaScript promise or an SDK completion.
- `fromCallback` and `subscribe` take calls from any thread, and apply them on the context that called them, in order ([lucent:core](/docs/api/lucent-core/#fromcallback)).
- The JavaScript promise of an `async` export settles on the JS thread.

No context waits for another to finish its work: what one hands another is posted. The only wait is for a package's lock, by the threads that run module code.
