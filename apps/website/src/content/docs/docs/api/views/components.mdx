A component is a function a `.lucent.tsx` module exports that returns a view. React mounts it as a native component, and its setup runs on the main thread. This page gives the rules for what a component exports and takes, and what React sees of it.

## Example

<Tabs>
<TabItem label="counter.lucent.tsx">

```tsx title="counter.lucent.tsx"
import { appContext } from "lucent:android";
import { TextView } from "lucent:android/android.widget";
import { UILabel } from "lucent:ios/UIKit";
import { PLATFORM } from "lucent:platform";
import { type Coalesced, effect, expose, signal } from "lucent:ui";

export function Counter(props: {
  label: string;
  step?: number;
  onReset?: (last: number) => void;
  onChange?: Coalesced<(count: number) => void>;
}) {
  const count = signal(0);
  const set = (value: number) => {
    count.set(value);
    props.onChange?.(value);
  };

  expose({
    increment: () => set(count.peek() + (props.step ?? 1)),
    reset: () => {
      props.onReset?.(count.peek());
      set(0);
    },
    value: (): number => count.peek(),
  });

  if (PLATFORM === "ios") {
    const label = new UILabel();

    effect(() => {
      label.text = `${props.label}: ${count.get()}`;
    });

    return label;
  }

  const text = new TextView(appContext());

  effect(() => {
    text.setText(`${props.label}: ${count.get()}`);
  });

  return text;
}
```

</TabItem>
<TabItem label="App.tsx">

```tsx title="App.tsx"
import { useRef } from "react";
import { Button, View } from "react-native";
import * as counter from "./counter.lucent";

const { Counter } = counter as unknown as typeof import("./.lucent/native/types/views/counter");

type CounterRef = { increment(): void; reset(): void; value(): Promise<number> };

export default function App() {
  const ref = useRef<CounterRef>(null);

  return (
    <View>
      <Counter ref={ref} label="Taps" onChange={(n) => console.log(n)} style={{ height: 44 }} />
      <Button title="+1" onPress={() => ref.current?.increment()} />
    </View>
  );
}
```

`Counter` takes two props, `label` and `step`, and sends two events, `onReset` and `onChange`. Its ref has two commands, `increment` and `reset`, and one request, `value`. The guides put each part to work: [state and events](/docs/guides/views/state-and-events/), [commands](/docs/guides/views/commands/) and [children](/docs/guides/views/children/).

## What makes an export a component

An exported function of a `.lucent.tsx` module is a component when every value it returns is a view. The module's other exports are module functions, which JavaScript calls as usual.

| The function returns | Platform | The host shows |
| --- | --- | --- |
| A `UIView`, or an instance of a subclass | iOS | That view. |
| An Android `View`, or an instance of a subclass | Android | That view. |
| JSX of SwiftUI views | iOS | A `UIHostingController` Lucent makes for each mount. |
| JSX of Compose elements | Android | A `ComposeView` Lucent makes for each mount. |
| JSX of UIKit or Android views | iOS, Android | The view of the tag it returns: for a `Flex`, the container view Lucent lays out. |

[SwiftUI and Compose in JSX](/docs/api/views/swiftui-and-compose/) and [UIKit and Android views in JSX](/docs/api/views/platform-views/) give the JSX rules. A component also follows these rules, and breaking one fails with [LUCENT3020](/docs/api/diagnostics/#lucent3020):

- It's an `export function`, or an `export const` of an arrow or function expression that declares no other name.
- It returns its view on every path, and synchronously. A promise of a view fails, and so does a view on some paths and another value on others.
- It takes one props object, or nothing. Destructuring the props fails: setup runs once, so read `props.name` where you use the value.
- It has no type parameters.
- Lucent code doesn't call it or use it as a value: only React mounts it.
- Its module belongs to a package: a Lucent package's own, or for an app module the nearest `package.json` above it, which must have a `name`.

## Props

Each member of the props object that isn't a function is a prop. A prop's type is plain data, which [LUCENT3021](/docs/api/diagnostics/#lucent3021) checks:

| Type | Allowed | Rule |
| --- | --- | --- |
| `number`, `boolean`, `string` | yes | |
| A union of string literals, `"s" \| "m"` | yes | |
| `T[]` | yes | `T` follows these rules. An element can't be `undefined`: use `null`. |
| An object type declared in Lucent code | yes | Its fields follow these rules. It has no index signature and doesn't contain itself. |
| `T \| null` | yes | |
| `name?: T`, or `T \| undefined` | yes | The prop may be missing. |
| `bigint` | no | Pass a number or a string. |
| A union of different types, `string \| number` | no | A view value has one type. |
| A tuple | no | Use an object. |
| A class instance, a `Date`, a `Map`, a `Record`, a native object | no | Only plain objects with declared fields cross. |
| A function | as an event | See [Events](#events). |

A missing prop and `null` are different values. Setup reads `undefined` for a prop JavaScript leaves out, and `null` for one it sets to null.

These names belong to React or to the host, and fail as props:

| Name | Why |
| --- | --- |
| `key`, `ref` | React keeps them. |
| `children` | React keeps it, unless its type is `Children`: see [Children](#children). |
| `style` | The host keeps it for the view's React Native style. |

Setup runs once per mount, so read a prop where its value is used. An `effect`, a SwiftUI or Compose body and a JSX attribute read it again after a commit changes it.

Setup reading a prop in its own code, outside the functions it makes and outside JSX, warns with LUCENT3021: that value never changes. Setup using `props` as a whole, such as passing it on or copying it, fails with LUCENT3021.

## Events

A function prop is an event. JavaScript passes the callback, and calling the prop in setup code, `props.onReset?.(last)`, posts its arguments to JavaScript. An event follows these rules ([LUCENT3021](/docs/api/diagnostics/#lucent3021)):

- Its name is `on` and a capital letter: `onChange`, not `changed`.
- It returns nothing. JavaScript runs the handler later, so it can't answer: give the view the value as a prop instead.
- Its parameters are plain data, as props are, and may be optional. A rest parameter fails.

An event reaches JavaScript only while React passes a handler for it, and until the mount ends. Native code never waits for the handler. A view's events arrive in the order the view sent them.

### Delivery

How JavaScript hears an event depends on its type. `Continuous` and `Coalesced` come from [lucent:ui](/docs/api/views/lucent-ui/#continuous).

| The prop's type | Delivery | JavaScript hears |
| --- | --- | --- |
| `(v: T) => void` | discrete, the default | Every event, at React's discrete priority, as for a tap. |
| `Continuous<(v: T) => void>` | continuous | Every event, at a lower priority: React may batch the updates they cause. |
| `Coalesced<(v: T) => void>` | coalesced | The latest value. A new event replaces the view's waiting event when that is the latest one and of the same type. |

Marking an event both ways fails. Mark an event `Coalesced` when only its latest value counts.

## Commands and requests

`expose()` from [lucent:ui](/docs/api/views/lucent-ui/#expose) gives the component's React ref its methods. Call it once, as a statement at the top level of setup, with an object literal of functions. Each function is a command or a request, by what it returns:

| The function returns | It is | The ref's method returns |
| --- | --- | --- |
| Nothing (`void`) | A command | `void` |
| A value of type `T` | A request | `Promise<T>`, resolved with the value |
| `Promise<T>` | A request | `Promise<T>`, settled when the function's promise settles |
| `Promise<void>` | A request | `Promise<void>` |

`expose()` may stand in a [PLATFORM branch](/docs/api/language/platform-code/#branches) at the top level of setup instead, once on each platform. Then each platform's commands can use its own view.

Commands and requests run on the main thread. Their arguments and results are plain data, as props are: a result may be `null`, but not `undefined`.

These fail with [LUCENT3021](/docs/api/diagnostics/#lucent3021):

- `expose` called twice on one platform, inside an `if` other than a platform test or a loop, or in a function setup makes.
- `expose` given a variable rather than an object literal.
- A member of the object that isn't a function.
- `expose` called outside a component.

JavaScript sees these errors from a ref:

| When | What JavaScript sees |
| --- | --- |
| The view isn't mounted: before React attaches it, or after it unmounts. | A command throws an `InvalidStateError`, and a request rejects with one. |
| The component unmounts before a request is answered. | The request rejects with an `AbortError`. A later answer is dropped. |
| A request's function throws, its arguments don't parse, or setup failed. | The request rejects with an `Error` carrying the message. |

A request's promise settles exactly once. An aborted request doesn't stop the work its function started: stop that work with [onDispose](/docs/api/views/lucent-ui/#ondispose).

## Children

A component takes React children when its props declare `children?: Children` or `children: Children`, with `Children` from [lucent:ui](/docs/api/views/lucent-ui/#children). Its setup makes their container with `slot()` and puts it in the view it returns.

<Tabs>
<TabItem label="card.lucent.ts">

```ts title="card.lucent.ts"
import type { View } from "lucent:android/android.view";
import type { UIView } from "lucent:ios/UIKit";
import type { Children } from "lucent:ui";

export type CardProps = { children?: Children };

export declare function Card(props: CardProps): UIView | View;
```

</TabItem>
<TabItem label="card.ios.lucent.tsx">

```tsx title="card.ios.lucent.tsx"
import { UIColor, UIView } from "lucent:ios/UIKit";
import { slot } from "lucent:ui";
import type { CardProps } from "./card.lucent";

export function Card(props: CardProps): UIView {
  const card = new UIView({ origin: { x: 0, y: 0 }, size: { width: 0, height: 0 } });
  const content = slot<UIView>();

  card.backgroundColor = UIColor.secondarySystemBackground;
  card.addSubview(content);

  return card;
}
```

</TabItem>
<TabItem label="card.android.lucent.tsx">

```tsx title="card.android.lucent.tsx"
import { appContext } from "lucent:android";
import { ViewGroup } from "lucent:android/android.view";
import { FrameLayout } from "lucent:android/android.widget";
import { slot } from "lucent:ui";
import type { CardProps } from "./card.lucent";

export function Card(props: CardProps): FrameLayout {
  const card = new FrameLayout(appContext());
  const content = slot<ViewGroup>();

  card.setBackgroundColor(0xffeeeeee);
  card.addView(content);

  return card;
}
```

</TabItem>
</Tabs>

These rules hold, and breaking one fails with [LUCENT3021](/docs/api/diagnostics/#lucent3021):

- The slot is the platform's container class: `slot<UIView>()` on iOS, `slot<ViewGroup>()` on Android.
- Setup calls `slot()` once, in a `const` at its top level. So a component taking children is written as platform files: in one file, each platform's slot would stand in a branch.
- Children without a slot, a slot without children, and setup reading `props.children` fail.

React Native creates, lays out and removes the children: don't add or remove the slot's subviews in setup. Nothing checks this.

React sees `children?: ReactNode`, or `children: ReactNode` when the prop is required. A component that takes no children renders none, and logs an error the first time JavaScript passes some.

## One file or platform files

A component is one shared `.lucent.tsx` module with [platform branches](/docs/api/language/platform-code/), or a declaration file and a platform file for each platform.

| Form | Files | Write it for |
| --- | --- | --- |
| One file | `counter.lucent.tsx`, with `if (PLATFORM === "ios")` branches | Components whose setup makes their views, and SwiftUI and Compose bodies. |
| Platform files | `card.lucent.ts` with an `export declare function`, then `card.ios.lucent.tsx` and `card.android.lucent.tsx` | Components that take children, and components returning UIKit or Android JSX on both platforms. |

React sees one component on every platform, so [LUCENT3023](/docs/api/diagnostics/#lucent3023) holds these rules:

- Its props, events and commands are the same on every platform, and its props, events and children are those the declaration file declares.
- A component on one platform is a component on every platform compiled.

In one file, leave the return type out: a type naming both platforms' classes, such as `UIView | View`, fails with [LUCENT3004](/docs/api/diagnostics/#lucent3004). A declaration file declares that union. For SwiftUI and Compose bodies it declares `View | ComposeView`: SwiftUI's `View` from `lucent:swiftui`, and `ComposeView` from `lucent:compose`.

## What React sees

JavaScript imports a component from its module like any export. `lucent build` writes each module's components as React sees them to `.lucent/native/types/views/<module>.d.ts`. Your app's TypeScript still resolves `./counter.lucent` to the module's source, so cast the import to the generated type, as App.tsx does.

| Member | React type |
| --- | --- |
| Each prop | Its plain data type, optional where the prop may be missing. |
| Each event | `(…parameters) => void`, optional where the event is. |
| `children` | `ReactNode`, when the component takes children. |
| `style` | `StyleProp<ViewStyle>`: the host view's React Native style. |
| `ref` | `Ref<{ … }>` of the commands and requests, when the component exposes any. |

React Native's other `View` props, such as `testID`, don't reach the view. A component that takes no children, and whose style gives it no size, is sized by its content.

## Mounts and recycling

A mount is one run of setup on one host view, for as long as that view shows that component instance. Setup, its effects, its commands and the callbacks it gives the platform run on the main thread. There they never take the lock module code shares: see [Concurrency](/docs/api/language/concurrency/).

- A commit runs again the effects that read a changed prop. Setup doesn't run again.
- A mount ends when React unmounts the view, when JavaScript reloads, and when React Native recycles the host view. Its effects stop, and its [onDispose](/docs/api/views/lucent-ui/#ondispose) cleanups run.
- A recycled host view starts a new mount: setup runs again, and its signals start from their initial values.
[How native views work](/docs/architecture/views/#setup-runs-once-per-mount) says when each platform recycles host views, and [its limits](/docs/architecture/views/#limits) list what views can't do yet.

## Diagnostics

| Code | What fails |
| --- | --- |
| [LUCENT3020](/docs/api/diagnostics/#lucent3020) | An export that returns a view but can't be a component, or Lucent code that calls a component. |
| [LUCENT3021](/docs/api/diagnostics/#lucent3021) | A prop, event, command or slot that breaks these rules, or a name React or the host keeps. Also `props` used as a whole, and setup giving the platform an instance of a Lucent class: give it a function. A prop read once in setup warns. |
| [LUCENT3022](/docs/api/diagnostics/#lucent3022) | Setup code that can't run on the main thread: module state, code the compiler can't follow, or native code unfit for it. |
| [LUCENT3023](/docs/api/diagnostics/#lucent3023) | Props, events or commands that differ between platforms, or a component on one platform only. |
| [LUCENT3024](/docs/api/diagnostics/#lucent3024) | A SwiftUI or Compose body Lucent can't write out: see [SwiftUI and Compose in JSX](/docs/api/views/swiftui-and-compose/#diagnostics). |
| [LUCENT3025](/docs/api/diagnostics/#lucent3025) | UIKit or Android JSX Lucent can't make: see [UIKit and Android views in JSX](/docs/api/views/platform-views/#diagnostics). |
